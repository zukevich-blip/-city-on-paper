# Масштабирование City on Paper: честный каталог городов и источников

Состояние на 9 ноября 2026 года. Это работа в ветке `feature/global-city-registry-audit-20261109`, отдельная от парижского исследовательского PR #44.

## Что есть и что не следует преувеличивать

- В `eras/data/atlas.json` **186 записей** и **342 привязки произведений**, но среди них встречаются отдельные объекты, которые нельзя механически считать городами.
- **303 уникальные архивные URL** среди 342 привязок. Наибольший повтор: `https://foto.biblhertz.it/obj08003574`, 40 упоминаний. Это может быть общий идентификатор альбома/архива, а не 40 одинаковых предметов: удаление запрещено до предметной проверки.
- В `data/curation/world-cities-v1.json` **150 поисковых городов**. По консервативному совпадению названия+страны с атласом совпали 72; новые **78 записей** не имеют подтверждённых координат или произведений.
- Совокупно получается **264 непроверенные географические позиции**. Среди них **44 имени с круглыми скобками** требуют проверки, являются ли они собственно городами, а не отдельными архитектурными объектами.
- **150 поисковых заданий** в очереди, из которых 78 ведут на ранее отсутствовавшие позиции. Никакие новые изображения ими пока не получены.
- Ни одно значение в `global-city-registry-draft.json` не объявлено независимо подтверждённым.

## Воспроизводимый офлайн-аудит

```bash
python -m tools.curation.audit_global_cities --out /tmp/city-global-audit
python -m pytest -q tests/test_global_city_audit.py
```

Выходы:

1. `global-city-registry-draft.json`: единые исследовательские записи со статусами `existing_atlas` / `seed_candidate_only`, известными или отсутствующими координатами и базовой статистикой.
2. `global-city-audit-report.json`: пересечения списков, повторы ссылок, неоднозначности, перечень подключённых и недоступных API.
3. `global-discovery-queue.json`: воспроизводимые **неисполненные** запросы поиска, явно `queued_not_fetched`.

GitHub Actions `Global city registry audit` собирает эти документы для инспекции в ZIP `world-city-registry-research-audit`. Никаких сетевых вызовов и изменений действующего музея в этом этапе нет.

## Архитектурные границы

- Существующие сборщики `tools/curation/build_world_graphics.py` (Wikimedia Commons) и `tools/curation/expand_open_archives.py` (Cleveland, AIC, Met) **сохранить и расширять**, а не писать заново.
- Официальный [LoC JSON API](https://www.loc.gov/apis/json-and-yaml/requests/endpoints/) подходит для дополнительного адаптера. Выход из поиска должен быть кандидатом без автоматической публикации. `fo=json` и валидный идентификатор объекта не доказывают HD, права или географию.
- [Europeana](https://www.europeana.eu/en/how-to-register-for-and-manage-an-api-key) требует API-ключ. Не выдумывать доступ; запуск через секреты после получения ключа.
- [Wikimedia API limits](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits): отслеживать 429/503, `Retry-After`, соблюдать User-Agent и лимит соединений. Использовать возобновляемую очередь с checkpoint и кэшем.
- Модели данных разделить на `city` (подтверждённая география), `site` (архитектурный объект), `artwork` (уникальная музейная работа), `holding` (конкретная музейная запись), `appearance` (присутствие в каталогах разных городов), `historical_map` и `review`.
- Город и площадка/памятник могут иметь разные ID; географическая идентификация должна иметь `source_url`, `wikidata_qid` или иной авторитетный идентификатор и `place_kind`. Совпадение названий+стран пока остаётся лишь рабочим ключом, не основанием для слияния.
- Нет права массово скачивать чужие изображения без проверенной лицензии. Создавать кандидатов с ссылкой на хранителя, затем проверять rights/IIIF/HD/атрибуцию. Витрину наполнять только по пройденным правилам.

## Реалистичные этапы и метрики

**Этап 1. География.** Довести 264 позиции до проверенного реестра городов и отдельных объектов. Использовать идентификаторы и справочники, исправить неоднозначности. Затем расширять кандидатный список до 1000+. Количество кандидатов и подтверждённых городов считать отдельно.

**Этап 2. Международный поиск.** Обработать 150 имеющихся запросов маленькими возобновляемыми партиями. Отчёт: сколько реально обработано, сколько ошибок 429/503, сколько оригинальных музейных идентификаторов и прав. Дополнить LoC, затем BnF/Gallica, Europeana по ключу, другие архивы при подтверждённых условиях.

**Этап 3. Каталог произведений.** Дедуп по `institution + object_id` и иным авторитетным ID, хранить несколько источников одного объекта. Не удалять совпадающие фото или изображения автоматически из-за идентичной страницы альбома или одинаковых названий.

**Этап 4. Исторические карты.** Искать карты независимо от литографий. Для каждого города возможны 0, 1 или много карт. Статус `unlocated`, `approximate`, `reviewed` или `accepted` отражается отдельно. Не требовать RMS <20 м для всех исторических эпох: не существует универсальной оценки пригодности старого плана.

**Этап 5. Публикация и UX.** Сначала статические страницы, JSON-каталоги, пагинация и кеш, затем серверный поиск/API при необходимости по реальной нагрузке. Тест браузера на ширине 390 px не равен тесту Safari на физическом iPhone.

## Отклонённые пункты прежнего плана

- **«1000 городов, 50 000 произведений, 500 проверенных геопривязок за шесть недель»**: исследовательские целевые ориентиры, не критерии приёмки MVP и не обещание сроков.
- **«80% данных автоматически»**: неопределённый знаменатель. Измерять отдельно автоматизированное извлечение кандидатов и долю прошедших авторскую проверку.
- **«0% дублей»**: ошибочный абсолютный показатель. Отдельно считать подтверждённые дубли и допустимые множественные представления работ.
- **«RMS <20 метров для всех карт»**: не универсальный научный стандарт. Нужен набор независимых точек и допустимая локальная точность по задаче.
- **«Обновить package.json»**: на текущей release-ветке файла нет. Не создавать фиктивную версию npm-приложения только ради релиза.
- **«Запустить новый релиз после технической проверки»**: PR #44 требует научной приёмки до выпуска спорных геопривязок. Мировой каталог может развиваться и выпускаться отдельно, по собственному evidence gate.
